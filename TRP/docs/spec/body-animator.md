# The body's animator

How the game animates the player's body, and what the first-person view and the movement take from it. Written from a reading of the game's code and of the controller and clips in the install; nothing here is copied from either.

## Which animator runs

The game has two ways to animate a body.

- **Unity's own animator** with the full controller `Player_anim_controller` (22 layers, generic clips of about 175 bone tracks).
- **Its own "fast" animator**, a reimplementation in the game's code that walks a baked copy of the controller, takes blend weights and average speeds from the precomputed root motion table, and plays clips through a mixer. A cut-down "spirit" player can run beside it.

Which one is chosen comes from `client.config.json` beside the executable (`UseBodyFastAnimator`, `UseSpiritPlayer`). This install has no such file, so both are off, and an offline raid switches the spirit off regardless. **The local player's body therefore runs on Unity's animator with the full controller.** A recording confirms it: the weapon in a sprint only fits when the synchronised hands layer is included, and the root motion table has no such layer. (An earlier second sign, a swing of walking pace within each stride, was a misreading of the game's velocity figure; see below.)

The fast animator's source is still useful: it spells out, in readable code, transition rules that Unity keeps in native code, and the two agree wherever both are known.

## What hangs on it

- **Movement states.** Every state of the base layer carries a `PlayerStateContainer` script naming a movement state (`Idle`, `Run`, `Sprint`, `Jump` and so on), with a few settings: whether it is the default, whether root motion is off in it, a limit on turning speed, a look sensitivity, and how much the animation is allowed to steer. When the animator *enters* an animator state, which is when a transition into it starts, the movement code leaves its current movement state and enters that one. Several animator states can name the same movement state; going between two of those re-enters without the full exit and entry.
- **Motion.** Each animator update, the state that is current for the movement code takes the animator's root motion for the frame (`deltaPosition`) and passes it through its own handling (inertia for walking, and so on), then projects it on the ground, adds gravity, limits it and moves the character. So the movement formulas in `movement.md` act on what the animator produces; they do not produce the motion themselves.
- **Curves.** Clips carry float curves named like animator parameters. The animator writes the blended value into the parameter every frame: `FootStep` (its sign flips at each foot plant), `Weapon_3rd`, `First_Person_Curve_Weight`, `Hand_Left`, `Hand_Right`, `Shoulder_Left`, `Shoulder_Right`, `Position_cache`, `Leftstance_curve`, `Mouse_look`, `Aiming_Layer` and others. Game code reads them back with `GetFloat`.
- **Bones.** The ribcage's place sets where the first-person rig and camera sit; the body's weapon bone carries the first-person weapon when the curves say so (`weapon-handling.md`, "Carried by the body"); `Camera_animated_3rd` lends its rotation to the camera.

## Parameters

The controller has 97 parameters: floats, integers, booleans and triggers, each with a default. The game sets them through `PlayerAnimator`. Those the movement uses:

| Parameter | Set from |
|---|---|
| `Speed` | the smoothed speed setting (0 to 1) |
| `Direct_X`, `Direct_Y` | the movement direction, each -1 to 1 |
| `Level` | the smoothed stance, 0 crouched to 1 standing |
| `Tilt` | the smoothed lean, -5 to 5 |
| `Inert` (and `InertFloat`) | raised while the player is asking to move |
| `Sprint` | raised once the sprint may start |
| `SprintSpeed` | the sprint's own speed, 0 to 2 |
| `IsJumping`, `Landing`, `FallingDown` | the jump's phases |
| `Aim_angle` | the view's pitch |
| `DeltaRotation` | the angle between view and body |
| `WeaponTypeFloat`, `WeapSizeModifier`, `ThirdPersonFloat` | the weapon's kind, its width in inventory cells, and 0 in first person |
| `TransitionMultiplier` | how fast stance-change clips play |
| `Step`, `IsGrounded`, `Prone`, `Direct` | sidestep, ground contact, prone, and the direction as one number |

A parameter with the same name as a curve is driven by the clips instead. Where the clips blending on the first layer do not all carry the curve, a clip without it stands for the parameter's default (0 for every such parameter here): going from lying still, whose clip has no `Hand_Right`, into the crawl, whose clips hold it at 1, the parameter rises with the blend and does not jump. Found by the fifth recording, in how the weapon comes to the hand as a crawl starts (`weapon-handling.md`, "In the body's hand"). A layer above the first leaves the value below alone as far as its clips lack the curve.

## States and how one gives way to another

Sub-state machines are flattened: every state has a full name such as `Base Layer.StateMachine_Move.MOVE`. A layer has one current state and, during a transition, a next state.

A state has a speed, optionally a parameter that multiplies it, and a motion: one clip or a blend tree. Its length in seconds is the motion's length divided by the speed.

Each transition has:

- **conditions**, all of which must hold: a boolean is or is not set; a float or integer is greater than, less than, equal to or not equal to a threshold; a trigger is set (and is cleared when the transition is taken);
- optionally an **exit time**, a fraction of the state: the transition may only start on the frame in which the state's time passes that point. A point in the first cycle comes round once per cycle, **whether the state loops or not**: a state whose clip does not loop still counts its time on past 1, and a condition that comes true after the point has gone by waits for the next crossing. (Settled 2026-10-11. The game's own animator code tests it so, `AnimatorControllerTransition.IsTimeForTransition`: the frame's two ends taken within the cycle and the point between them. And the weapon's animator is recorded doing it: `DRY FIRE`, which does not loop, with a way out "at 1 once the trigger is up", is left only at a cycle's end, two cycles in where the trigger came up at 1.44. Until then the engine here took such a point in a state that does not loop as passed for good once passed. The body's recordings cannot tell the two apart: all fourteen replay line for line the same either way.) A point past the first cycle is passed once;
- a **length**, in seconds or as a fraction of the state being left;
- an **offset**, the fraction of the next state at which that state starts;
- a setting for whether a transition under way may be **interrupted** by another from the state being left, the state being entered, or either in a given order.

Each frame, with no transition under way, the layer tries the transitions that may be taken from any state, then the current state's own, in the stored order, and takes the first whose conditions and exit time are met. A destination can be the entry or exit of a sub-state machine, which is a list of further conditional choices followed to a real state.

During a transition both states keep playing, each at its own speed, and the blend weight of the next state rises in a straight line from 0 to 1 over the transition's length. The next state's enter callback fires when the transition starts; the old state's exit callback fires when it ends. A transition of no length changes state at once.

**Where in the frame a transition starts.** One that waits for an exit time starts at that point, not at the frame's edge: what is left of the frame after the point goes to the blend and to the next state. One started by a condition alone starts with the frame over: its next state is at its offset, with no time run, when the frame ends. Recorded at 120 frames a second: the landing clip passes its exit point (0.85) 0.29 of a frame before a frame ends, the walk it blends into stands at 0.29 of a frame's worth of its own time, and the blend of 0.06 s is over after seven more frames, not eight; the standing clip entered when a jump lands, by a condition, stands at exactly 0. A transition with no blend at all is no exception: taken at an exit point it too gives the rest of the frame to its next state. Recorded (sixth recording): the sidestep's way in ends 0.08 of a frame into a frame, and the hold it enters with no blend stands 0.92 of a frame on (0.0576 of its 0.133 s) when that frame ends; the simulation had it at 0 until this was put in.

**A transition cut short** (settled by the thirteenth recording, 2026-10-10; nothing in the game's code says any of it, the engine does it). A transition under way from A into B that allows it can be cut short by one out of B into C. The vault's way out is the recorded case: `Vault` blends into `Vault_Land_Idle` at its exit point, and one frame later `Vault_Land_Idle`'s own way into `MOVE` (open whenever a movement key is held) cuts that short. What the engine then does:

- **The blend of A and B is held still, as the frame before the cut left it,** and C is blended into out of that. The frame of the cut shows what the frame before showed. Recorded: a curve only the entered states carry (`FootStep`, which the walk has at 1 and the vault's states do not have at all) reads on the frame of a second cut exactly what it read the frame before, and through the blend it reads C's weight and nothing else.
- **A goes on being reported as the current state.** Its own clock moves on once more in the frame of the cut and stands still from then on (recorded: 0.6007, 0.6100, and 0.6100 for the next fourteen frames), and the engine names it, not B, as the state the transition leaves.
- **The held blend goes on moving the root as it last did:** the travel it gave in the frame before the cut, a second, by what is left of its weight. Recorded: with this the walk's pace out of a vault is the game's on every frame of the blend (2.22, 2.10, 2.50, 2.63, 2.77, 2.58, 3.04 m/s by the game's own figure), and the sprint's out of a sprint's vault likewise; held with no motion of its own the first is 0.13 m/s slow all through.
- **The new blend's length, where it is a share of the state:** not that share of B, which it leaves (`Vault_Land_Idle` is 0.133 s long and the share 0.1: 0.013 s), nor of A. Recorded twice, with A a vault and a sprint's vault: C's weight is C's own progress over 0.08, so the blend takes 0.08 of the *walk's* cycle (0.1205 s and 0.1067 s for walks 1.506 and 1.333 s long, tracking the walk's length frame by frame as the speed setting moves it). 0.08 is the share (0.1) over 1.25, and 1.25 is the pace both held states were playing at (`Vaulting_speed`). **Taken as: the share, of the state being entered, over the pace of the state held**, first provisionally (both recorded cases have the same share and the same pace, so the two readings, over the pace or times a plain 0.8, could not be told apart), since 2026-10-18 read in the engine (`UnityPlayer.dll` decompiled: while a blend is held, the length the share is of is the entered state's, which `EvaluateState` keeps as it evaluates that state, over the speed `ComputeStateSpeed` gives the state still reported). **The entered state's length is at its clips' own pace**, its own speed not counted (recorded 2026-10-31, `courses8\akm-blind-restrictions` at 19.55 s: blind fire's way out to the right, at speed 1.3 and 1.233 s long, entered by a share of 0.2 out of the way out over the top held at 1.3, blended in 0.19 s, 0.2 × 1.233 ÷ 1.3; with its own speed counted as well it came to 0.146 s, a quarter short, until 0.164.3; the walks above play at their clips' pace, so the vaults' blends did not tell the two apart). A length in seconds is left as it is. The engine also holds the blend on a cut from the side of the state being left (`StartInterruptedTransition` is called for every interruption), which this work does not yet do (below).
- **A blend out of a held blend can be cut short again** (recorded: out of a sprint's vault, `MOVE` is entered and three frames later the sprint cuts that short). What is held then is the old held blend and C, by the weights the frame before the second cut gave them; A is still the state reported.
- A's and B's exit callbacks: taken to fire when the blend out of them ends. Not recorded (nothing the game does hangs on them here).
- **Left open: what a held blend makes of the curves, after a second cut.** Through the first held blend the curve-driven parameters are the game's on every frame. Out of a sprint's vault, where the walk's blend is cut by the sprint's three frames in, they part for the 24 frames of that last blend: the game's `Weapon_3rd` and `First_Person_Curve_Weight` jump on the frame of the second cut from 0.833 back to 0.988 (what they were before the walk began to blend in) and then dip to 0.75 at the blend's middle before reaching 1, where the simulation's run straight from 0.83 to 1. The dip is what the hands' layer makes of a part it does not cover (`below + (1 - below) * weight`, with only the sprint covering it), and the jump is as if the walk, which has neither curve, no longer diluted what is held, though it still does for `FootStep`, which it does have. So a held blend seems to keep each curve by the states that carry it, and to have no part in a synchronised layer; one case is not enough to build on. The cost: for a fifth of a second after a sprint's vault the weapon is up to 6.5 cm and 37 degrees nearer the body's carrying pose here than in the game.

Built: `Held` in `animator`. A cut from the other side (by a transition out of A while A to B is under way) is as it was: B is dropped and A blends into the new state.

**Who is called in a frame.** A state's script is called to move the character on every frame its state has a part in: while it is the current state, while it is being blended into, and on the frame it is left. Two states of the same layer naming the same movement state therefore call on it twice in a frame they share (`movement.md`, "Looking").

## Blend trees

A blend tree's leaves are clips; inner nodes blend their children by one parameter (weights fall off linearly between neighbouring thresholds) or by two. Each child has a factor on its length (`m_Duration`, the inverse of its time scale).

All clips in a tree run in step: the tree's length is the weighted sum of its leaves' lengths, and every leaf is at the same fraction of its own length. A leaf's clip therefore plays faster or slower than real time unless it is the only one.

There are three two-parameter kinds, each child having a place in the plane of the two parameters:

- **Freeform Cartesian.** A child's influence at the sample is 1 at its own place and falls off linearly toward every other child, reaching 0 at that child; the smallest of these over all the others is its weight, and the weights are then scaled to sum to 1.
- **Freeform directional.** The same, but measured in direction and distance from the origin instead of x and y: the step from one child to another is (the angle between them in radians, the difference of their distances divided by the average of the two). A child at the origin has no direction, so against it only distance counts; for a pair one of which is at the origin the angle used is the sample's own angle from the other.
- **Simple directional.** At most one child at the origin, the rest around it. The sample lies in the wedge between the two children nearest in direction on either side; its weights are its barycentric coordinates in the triangle those two make with the origin, brought back to the triangle's edge if it lies outside. What falls to the origin goes to the child there, or is shared equally among all if there is none.

The install checks these. The root motion table stores, for 76 two-parameter trees, the engine's own weights over a grid of both parameters. The functions in `rootmotion` reproduce all 29 Cartesian grids and all 38 simple directional grids exactly, and the 9 freeform directional grids exactly wherever the sample lies among the children. Far outside them (ten times as far out as any child, or on the far side of the origin) the stored freeform directional weights differ from the computed ones by up to a half; nothing the simulation does takes a parameter there. (A weight on the angle of 2, as in the published description of this blend, does not fit the grids; 1 does.)

The body uses all three: walking blends Cartesian over direction and speed; the layer that bends the body with the view blends freeform directional over lean and stance and simple directional over the body's twist and the view's pitch.

## Root motion

A clip stores the path of the root as curves (`RootT` x, y, z and `RootQ`), bound to the animator itself with a marker saying they are motion curves, along with the root's place at the clip's start and end and its average velocity. The table's "velocity per clip" is that average.

The animator's motion for a frame is the weighted sum, over the clips playing on the base layer, of how far each clip's root moved between its previous and its new time, counting whole loops by the clip's start-to-end displacement. In a transition the two states' sums are blended by the transition's weight. The result is in the body's own axes; the game turns it by the body's rotation.

Each clip says, for the root's travel sideways-and-ahead and for its travel up-and-down separately, whether it goes out as root motion or stays in the pose (`m_LoopBlendPositionXZ`, `m_LoopBlendPositionY`). In every body clip looked at, level travel goes out and vertical travel stays. So the root bone keeps its vertical track: a jump clip lowers the root 0.35 m under a pelvis raised 0.365 m, which leaves the body where it was and lets the game's own jump arc carry it. Taking the vertical travel off the bone as well put the eye 0.37 m too high in a jump.

**Turning.** The root's rotation is stored the same way, as a quaternion in four more of those curves, and what it turns between two times goes out as the animator's rotation for the frame (`deltaRotation`); the standing-type states turn the body by it. Nearly every clip keeps it constant. The exceptions here are the four turns on the spot (`idle_Turn_L`, `Idle_Turn_R` and their crouched versions, 0.83 s long): each swings the root a quarter turn about the vertical in its first 0.4 s and holds it. The bone that carries the root's path (the pelvis) keeps its own track, which turns with the character, so the root's rotation has to come off it as the root's travel does: the bone's place and rotation are turned back by the root's rotation at that time. Without that the pose turned a quarter turn inside a body that had already turned one, and the eye swung 20 cm round the body during a turn.

Standing, the animator enters a turn with no blend once `DeltaRotation`, the angle from the body to the view, has passed 45 degrees either way. The parameter is a frame old (`movement.md`, "Looking"), so the turn starts on the frame after the view passes. Up to there the body only follows the view by the rule in `movement.md` ("Looking"). So a view turned 70 degrees leaves the body at 92: the little it had followed, and the quarter turn. The body ends ahead of the view. The code reads a `Turn` parameter while these states play and corrects the angle by it, but the controller has no such parameter, so the correction is nothing.

A view that stops between 135 and 180 degrees round gets two turns: after the first the body follows to 45 degrees behind, which is the threshold again, and a second quarter turn carries it 45 degrees past the view. Recorded: the view turned 140 degrees, the body 185.

The condition is *more than* 45, and a body that has been drawn after the view to the limit reads exactly 45 (`movement.md`, "Looking": the angle is rounded), so being held at the limit does not by itself start a turn. And since a quarter turn leaves the body up to 45 degrees *past* the view, a view turned back only a little after one is past the limit the other way and gets a quarter turn back: the feet step round again for a turn of the view of a few degrees. A turn asked for while the other still plays cuts into it, blending over a tenth of the turn's length from the new turn's start. All of that is recorded (eleventh recording; table under "Compared with the running game").

So starting to walk ramps up over the blend from standing into the walk rather than at once: 0.63, 1.57 and 2.82 m/s after 0.05, 0.1 and 0.2 s for an untrained character, where the recorded one (6% faster) shows 0.65, 1.6 and 3.0.

## Layers

A layer has a weight, a blending mode (override or additive), and a mask naming the bones it may move. Later layers are applied over earlier ones: an override layer replaces the masked bones by its weight; an additive layer adds the difference between its clip and that clip's reference pose, scaled by its weight.

A layer can be **synchronised** with another: it has no state machine of its own and plays, for whatever state the other layer is in, a blend tree of its own, at the other layer's time. `Sync_SprintHands` is such a layer over the base layer; for most states it has no tree and does nothing, and for the sprint it sets the arms and the body's weapon bone.

The game changes some weights at run time: layer 6 follows `1 - Aiming_Layer` every frame, and layers 17 and 19 are switched off for a player.

Float curves ignore masks: an override layer's curves replace the earlier layers' values by its weight.

**An additive layer's curves add, as its bones do.** What a clip on an additive layer gives a parameter is the curve's value now less its value in the clip's reference pose (its first frame), times the clip's weight in the layer and the layer's weight, added to what the layers below made of the parameter. Found in the seventh recording, where no reading of the code would have shown it. The layer that bends the body with the view (`Additive_Aiming`) blends nine clips by `DeltaRotation` and `Aim_angle`. Its centre clip (`idle_aim`) carries `Weapon_3rd` at 1 throughout; its side clips (`idle_aim_right` and the rest, 0.13 s long and not looping) carry it at 1.1 on their first frame and 1 after. The layer has been in that state far longer than 0.13 s, so each side clip stands at its end and gives 1 - 1.1: a tenth off `Weapon_3rd` for as much of a side clip as is blended in. With the view 25 degrees to one side of the body that is 25/45 of one: recorded, `Weapon_3rd` 0.9444 where the base layer's clip has 1 (28, 46 and 49, getting up; 45, a jump, 0.9546 at the 20.4 degrees of the frame before). It only matters while `First_Person_Curve_Weight` is above 0, where it lets the first-person weapon follow the body's a twentieth less. Built 2026-10-09.

**An additive layer's clips are blended before they are added** (settled against the recordings on 2026-10-09). Each clip of an additive layer gives, for each bone, its difference from its own reference pose: a shift, and the turn that takes the reference's rotation to the clip's. Where the layer's blend tree has several clips playing, those differences are blended with one another like the clips of any tree (shifts by their weights, turns summed as quaternions on one side of the sphere and made a unit again), with no turn standing in for any share of the layer that no clip fills, and what comes of it is added to the pose once, by the layer's weight. The first build added the clips one after another, each by its own weight. The two are the same for one clip and for turns about one axis, and part in the second order where the clips turn a bone about different axes, which is the layer that bends the body with the view (`Additive_Aiming`) whenever the view is both pitched and turned from the body, or pitched in a lean: its clips for "down" and for "to the right" turn the spine about different axes. Nothing in the game's code says which; the engine does it. The recordings do: added one by one, the first spine bone was up to 1.1 degrees out and the ribcage, with the eye on it, 3.0 to 5.5 mm root mean square through a lean or a turn of the view with the view 9.5 degrees down (tenth recording, scenarios 10, 11, 22), 2.1 to 3.7 mm at 6 degrees down (fourth), 0.1 mm with the view level (seventh); blended first, the spine bone is within the recording's rounding (0.06 degrees) and the ribcage and the eye within 0.05 mm in all of them. It grows with the pitch: in the simulation, with the view 60 degrees down, the old way had the eye up to 16 mm from where the new has it, a different way for each side the view is turned to (so it swung by twice that as the feet stepped round under a still view). The legs were never touched by it: none of that layer's clips moves them differently. Not recorded with the view far down and turned at once; recorder 0.4.6's scenario 59 is that.

**TRP's own: the bones followed, the bones carried, the mix and the pose made when asked** (an exception to rule 8, on purpose, for levels of detail and posing). Nothing here is the game's (whose own posing by distance and hold off screen, which move hits, are `third-person.md`'s, "What is drawn", and not built). TRP splits the work so that a host with many characters can make the costly part of a pose only when something needs it, with every result what the whole working-out gives. (1) **Each bone stands alone.** Through the layer stack, a bone's place and turn go by its own tracks, the frame's layer weights, each clip's share, time and weight, each layer's total and kept share, and (for a bone a layer leaves standing) its own place after the last update; never by another bone's. A clip's curves do too: each curve is sampled from its own keys, samples or figure, straight or smooth. (2) **Followed bones.** A controller is told which bones its host reads after each update: the body its 38 (root to ribcage, the camera, the weapon bone, both arms to the palms, the left fingers, the elbows' goals, the camera's container); a weapon in a character's hands the bones above the weapon root, the moved bone, the three markers and the sight's nodes (`puppet::followed_rig_bones`: 13 of the AKM's 167, 16 of the Rhino's 118, 9 of the empty hands' 62); the player's own weapons every bone. With them the root and any bone whose scale is kept are always worked out. Each clip is cut once in two: the curves of those bones with every curve that drives a parameter or carries the root, and the rest (a track two bones share, as the root asked for twice, goes into both). (3) **The mix.** An update steps the machines and keeps, per weighted layer, its weight, each clip's share with its two times, offset and direction, their sum and the kept share, as they stand before the update sets the parameters the clips drive; from it, it works out the curves, the root's travel and turn, the clips' events and the followed bones. (4) **Carried bones.** A bone a layer leaves as it stood (an override layer playing, by some share, a state with no motion on its slot that writes no defaults) goes by its own last place, so its pose carries from update to update. The controller marks at load the bones its layers' states as read may leave so (the Rhino's `Cylinder` layer: its cylinder, `mod_magazine`, and the root; none of the body's, the AKM's or the empty hands' states as read), but an update does not trust the mark: on each update it works out every bone a layer with a kept share moves, beside the followed ones, and the mix keeps them; where the last update did not work such a bone out, its last place is made from the last mix first. So a state asked for outright that the mark could not foresee (an unread one that writes no defaults: three of the body's) is carried too. (5) **The rest, when asked.** The pose of every other bone is a function of the mix alone, in the same arithmetic as the update's (`Controller::pose_of`); where nothing is deferred the update makes it at once. The pose for drawing (`SMOOTH ANIMATIONS`) has its own mix: TRP has always worked that pose out after the update set the parameters the clips drive, so its blend trees read them as set (a tree by a curve-driven parameter can weigh its clips otherwise than the pose's); kept so, its bones left standing kept with it. **Not exact, and not built on**: working a pose out again from the animator as it stands (`pose_with`, `pose_now`): the trees read the curve-driven parameters as the update left them, and a layer that leaves bones standing leaves them where this update put them, not the last; the drawing between frames uses it as before, and the posing economy uses the mix. **Compared**: the regression with every bone worked out at each update and with the body's drawn bones made from each frame's mix as the sample is written (`replay --posing deferred`), both to the bit as before; the body's, the AKM's, the Rhino's and the empty hands' poses from mixes kept 900 frames against the whole working-out, smooth and not, states asked for at random; every clip of the body and the AKM sampled split and whole (`posing`). (6) **The puppet's recipe and its two ways of being posed** (`third-person.md`, "Posing by distance and off screen", for the whole): a character no one is at the keys of (`trp_sim::puppet`) keeps, of each frame, the body's mix (`Body::posing_mix`) and the thing in hand's (`WeaponAnimator::posing`, the parts' with it), with the free look's turn as it then stood, which its drawn bones are turned by (`Body::drawn_bones_turned`: the turn is put on after the pose, so a later turn must not reach an earlier frame), and what the arms are solved by. Posed in full, its animators work every bone out at each update and the frame's pose is made from their poses as the frame ends; posed when asked, they are deferred (`Body::set_deferred_posing`, `Firearm::set_deferred_posing`, `EmptyHands::set_deferred_posing`, put on each frame before the update) and the frame's pose is made, when asked, from its recipe (`drawn_bones_turned`, `WeaponAnimator::pose_of`, `drawn_of`). The rig the simulation reads is posed from the animator's pose either way: deferred, its bones other than the followed hold their last working-out, and nothing reads them. The weapon's animator is split by the bones a puppet reads of it with the sight it picks (`puppet::sights_for`, `followed_rig_bones`); a host that does not split it loses nothing but the saving. An underbarrel launcher's animator is never deferred. **Compared**: posed in full and posed when asked, eight characters in lockstep, every asked pose and every pose drawn the same to the bit (`puppet` tests).

## How the movement code steers it

The base layer's states that matter here, with the movement state each names:

| Animator state | Movement state | Left by |
|---|---|---|
| `Stand.Idle_Aim` | standing (`Idle`) | to walking over 0.15 s when `Inert` is set and a direction is given (starting 0.12 to 0.28 into the walk's cycle by direction); to the sprint over 0.13 s; to a jump |
| `Stand.Turn_Left_90_Aim`, `Turn_Right_90_Aim` | standing (`Idle`) still | to standing at 0.95 of it; to the opposite turn if the view is past 45 degrees the other way; to walking or a jump |
| `Stand.SideStep_In_Right`, `SideStep_Right`, `SideStep_Out_Right` and the three for the left | the sidestep (`Sidestep`), each saying which part it is: the way in, the hold, the way out | from standing with no blend when `Step` asks; the way in to the hold at its end; the hold to the way out when `Step` no longer asks or `Inert` is set; the way out to standing at its end, or to walking (`movement.md`, "The sidestep") |

**Reloading.** Two parameters come from the weapon's logic, not the movement's (`firing.md`, "Reloading with a magazine"): the flag `ProneReload`, up while the reload operation is the one in hand, and `ReloadFloat`, 1 from the reload's start until the weapon's animator starts back into its rest.

- *`ProneReload` and the screen* (read 2026-11-01): the screen's opening and shutting set the flag too (`MovementState.OnInventory`), but only through hands that pass it on: the empty hands, a firearm, a knife and a usable item (`SetInventoryOpened`); an item's hands for using it and a grenade's do not. New hands ready (a firearm's, a grenade's or the empty hands' draw over) are told the screen's state again (`GamePlayerOwner.SetHandsController`, `Player.SetInventoryOpened`). Recorded (`courses8`'s eating): up as the screen opens with empty hands, still up after it shuts with the food in hand, down as the empty hands after it are ready.
- *`ReloadFloat` and the other hands* (read 2026-11-01): every hands' draw and put-away set it to 1 and the draw's end to 0 (`SpawnOperation`, `Remove`; a grenade's draw ends at `OnDrawCompleteAction`); an item's hands never touch it, so it stays at the 1 the put-away before them left until the next hands are drawn.

- *Lying down.* `Prone_Idle_Aim` and the crawl both leave for `Prone.Prone_Reload` when `ProneReload` is set, over 0.4 of the lying clip (0.053 s) and 0.2 of the crawl's cycle (0.32 s). That state plays the lying clip again, at half speed, and names the movement state lying still. Its only ways out wait for the flag to drop: to `Prone_Idle_Aim` with no blend, and to the crawl if `Inert` is set, which comes second and so is never the one taken. Nothing else leads out of it, not `Inert`, not `Prone`, not `Step`. So a reload stops a crawl and holds the body lying still until the new magazine is in: the movement keys, the roll and getting up all wait for that. A movement key still held then starts the crawl from `Prone_Idle_Aim`, as from lying still at any other time.
- *Upright* the flag is raised just the same and no state of the base layer answers it. The online raid's player refuses the prone key while it is up; the offline one does not, and a character sent down in a reload reaches `Prone_Idle_Aim` and goes on from there into `Prone_Reload` like any lying one (`movement.md`, "Prone"; recorded, seventh recording, 46).
- *The pose* is the lying one throughout, so the eye does not move; only the state, and the clip's own clock at half speed, differ from lying still.
- `ReloadFloat` drives two layers. `UtilityOperation` (the third) goes to a clip that reaches for the vest, standing or lying; the game sets that layer's weight each frame from how far the hand is from the vest, and only for a character seen from outside: for the player it is 0 on every recorded frame. Not built.
- *In a sprint* the other layer answers: `Sprint_ReloadHandsTrans` (the sixth, an override layer of full weight over the arms and the body's weapon bone). It rests in an empty state and, while `ReloadFloat` is above 0 and `Sprint` is set, blends over 0.45 s into `RELOAD`, a held pose (`sprint_slow_reload`) whose curves take the place of the sprint's: `First_Person_Curve_Weight` 0.35 where the sprint has 1, and the hands' and shoulders' curves 0. The body's hold on the weapon is the product of `Weapon_3rd` and that weight, so the weapon comes back two thirds of the way from where the sprint carries it to where the first-person motion has it, up into view, with both hands on it, and the reload shows. When `ReloadFloat` drops with the sprint still on, the layer blends back over the state's own length (0.27 s); if the sprint ends first, or the character goes down, it goes out through a second empty state over 0.4 s or 0.03 s. `ReloadFloat` is the weapon's hands being busy: a reload from its start to its animation's end, and a look at the weapon likewise (`firing.md`). Built 2026-10-08 from the install's states and clip. Compared with the game (seventh recording: a reload in a sprint, 41, and a look at the magazine in one, 43): `ReloadFloat` is the game's on every frame; the body's hold on the weapon, which is the product of the game's `Weapon_3rd` and `First_Person_Curve_Weight`, is the game's within 0.0003 on every frame, down to 0.35 and back; and the weapon is within 6 mm and 2.2 degrees of the game's through the reload and 12 mm and 1.3 through the look.

The movement code only raises and lowers flags:

- Standing, a movement key sets the direction (the keys' signs times 0.01) and raises `Inert`. The walk begins when the animator's walking state does, the same frame.
- Walking, `Inert` is lowered when there has been no input for a while and the speed has run down, and also at the end of the short pause that follows a reversed input. That second case is why reversing goes through standing: the walk blends out for 0.15 s, the standing state raises `Inert` again at once, and the walk blends back in the other way.
- `Sprint` is raised from a walk once the sprint is wanted, the stance is above 0.9 and the speed setting has wound up to 1. Sprinting, letting go of forward or of the sprint key lowers it; in such a frame the sprint state does not move the character.
- A jump raises `IsJumping`; the jump proper starts when the animator enters a jump state. Touching down lowers it and raises `Landing`, with `Inert` and `Sprint` set by whether a direction is still held.
- The prone key raises `Prone` from anything upright and lowers it lying down. That is all the code does to go down or get up; the four movement states that follow are in `movement.md`, "Prone".

Each animator update the movement state that is current, if one of the animator's playing states names it, handles the frame: it takes the animator's motion and passes it on. While a landing clip with no movement state plays, nothing moves the character.

## Other things the body's animation gives

- **Footsteps.** In the walking and sprinting states the game watches the sign of `FootStep` each frame. A change of sign is a footstep if the last one was more than 0.2 s ago and the character has not been falling for long (1 s walking, 0.6 s sprinting). The time since the footstep before retunes the weapon's bob.
- **A lag in the body's height.** The body does not follow the feet up and down at once. Each frame it is pushed back by what the feet just moved vertically and eased home by a critically damped spring (0.066 s, or 0.3 of that while the gap is still opening), never more than 0.2 m away. Going up in a jump the eye trails below; coming down it rides above. The spring's time is itself eased toward whichever of the two figures applies, by `lerp(time, figure, dt)`, so it changes over about a second; the game starts it at zero when the character is made and it has reached 0.066 by the time anything is recorded. The simulation starts it at 0.066: started at zero it left the eye 5 cm high through a jump made in a scenario's first second. Two more things of it (`Player.HeightInterpolation`, read again on 2026-10-11). *Its time is the player's own clock*, the whole milliseconds the movement states go by (`_bodyTime`, which is what `ManualUpdate` was given), not the engine's frame time. The simulation had stepped it by the engine's, which is within half a millisecond of the other on an even frame and left the eye 1.2 to 4.5 mm out for a few frames of every recorded jump. The fourteenth recording has a frame where the two clocks differ outright (a hitch in mid-jump: the engine's frame 8.3 ms, the player's clock 75 ms), and there the eye was 13.9 cm out for that one frame. Stepped by the player's clock the eye is the game's to 0.05 mm on every frame of that recording, and through the jumps of the fourth to the thirteenth it is within 0.2 mm where it was within 4.5 (`08-jump-standing`, `09-jump-running`, `57-jump-from-sprint`; within 2 mm in `45-turn-jump`). *Lying down, the feet's move is not fed in* (the game takes it as nothing while the character is prone), so what is left of the lag eases home and a crawl over rising ground opens none; built so, and the crawl's pelvis is the game's to under 0.05 mm (it was 0.1). The game also sets the lag to nothing when the character is moved outright (`Teleport`) and on frames it does not draw the body in full; neither comes up here.
- **The jump's push-off** is multiplied by `1 + 0.2 * Strength / 50`.
- **Aiming** caps the speed setting at 0.33 (plus a skill bonus not read).
- **Aiming leans the body into the sights.** The animator has a flag `isAiming`. The firearm controller sets it to whether the sights are up each time that changes (unless a fitted part brings aiming animations of its own, which then run on the weapon's animator instead). An additive layer, `Additive_ISaim`, answers it. It rests in `NO_AIM`, which has no clip. With the flag up it goes at once, with no blend, to `idle_aim_AimIn`, or to `Prone_aim_AimIn` if `Prone` is set; the standing one picks its clip by `Level` (the stance), the lying one by weapon type. With the flag down that state blends over a tenth of itself into the matching `AimOut` state, which blends back into the `AimIn` one if the flag comes up again, and otherwise at 0.9 of itself into `NO_AIM`. The clips carry the ribcage, and with it the eye, about 14 mm, turn the arms a few degrees, and move the body's own weapon bone 3 cm. The layer has no say in the movement state. The sprint switching on puts the sights down (`firing.md`), so the flag drops then too, a quarter of a second before the sprinting state begins.
- **Each movement state has a top speed** the character controller enforces, and **a landing** caps the selected speed for a while. Both are in `movement.md`.

## The body as drawn (read and built on 2026-10-09; its legs compared with the tenth recording the same day)

**What the body is made of.** The player prefab has the skeleton and no skin. What is seen is clothing: the install's customization list (`templates/customization.json` in the SPT database) names a bundle for each of four parts of a character, `Body` (the upper body), `Feet` (the legs, boots and all), `Hands` and `Head`. Each bundle is a skinned mesh at two levels of detail with a `Skin` script on each, listed fullest first by a `LoddedSkin` on the bundle's root. (A `LoddedSkin` lists skins, `_lods`, once `Skins`, all set up and switched on and off together: `LoddedSkin.Init`, `EnableRenderers`. They are levels of detail only where a `LODGroup` on the bundle chooses among them, as on clothing and heads. Hands bundles have none, and each skin listed is drawn: six list a watch's case, and on some its glass, as skins of their own beside the hands, the Phoenix's two, the Nord's, the Instructor's, USEC's Clawgear and Special Ops. Before, the first skin alone was taken, and the BEAR Phoenix's and Instructor's hands showed no watch.) A `Skin` names its mesh's bones by their path on the player's skeleton (`Root_Joint/Base HumanPelvis/...`), 48 of them for a shirt. The first-person arms are the `Hands` part of the same scheme. The default BEAR set is `tshirt_bear_turtleneck`, `pants_bear_srvv`, `bear_hands_skin` and `bear_head_0`.

**What poses it.** The body's animator, which poses every bone of the skeleton its clips have tracks for. The legs, the pelvis and the spine are its alone.

**What first person does to it** (`FirstPersonStrategy.ApplyFovAdjustments`, started from the end of the player's late update and undone after the frame is drawn; `Player.SetShoulders`, `IkApply`):

- The ribcage bone is turned to where the player looks (the rotation the weapon's rig has) and then scaled (1, 1, s) in its own axes, s being the squeeze of a wide field of view (0.65 at 75 degrees, 1 at 50). Both only when the squeeze is not 1: at the narrowest field of view the ribcage is left as the animation has it.
- Three transforms are put back where they were before the turn, in place and turning: the two collarbones and the body's weapon root (`PlayerBones.FovSpecialTransforms` on the player prefab). The scale comes after, so their places are still drawn in along the view with everything else under the ribcage.
- Whatever else hangs from the ribcage turns and is squeezed with it. The neck and head do not hang from it: the head's skin names its bones as the last spine bone, the neck under that, and the head under the neck (`Base HumanSpine3/Base HumanNeck/Base HumanHead`), beside the ribcage like the body's weapon bone. So the head stays where the body's animation has it, unturned and unsqueezed. (An earlier reading here had the neck under the ribcage; the head's bundle says otherwise.)
- The arms are solved onto the weapon (`hands-on-weapon.md`): the upper arm is put on the weapon rig's, and the forearm and palm follow the solver.
- **Not all of it is drawn to its own player** (`PlayerBody.UpdatePlayerRenders`; read on 2026-10-09: the game shows the body from the hips down only). Of the four parts, in first person: the legs (`Feet`) are drawn as always; the hands are drawn, and only in first person; every other part, which is the upper body and the head, has its renderers set to cast shadows and nothing else. From outside (third person) the upper body and head are drawn in full and the first-person hands are switched off. **Recorded** (tenth recording, the header of all 56 traces, which is the first renderer of each part as the game had it): point of view `FirstPerson`; `Feet` on, casting shadows; `Hands` on, casting none (that is how their renderers are made; no code sets it); `Body` and `Head` on, shadows only. The app's hands cast a shadow until then; they no longer do.

**Built** in the app (`body_view`; `trp_data::arms::load` reads any part's fullest skin; `BodyData::load_with` and `Body::drawn_bones` in the simulation pose the bones a host names). The clothing's bones that are not an arm's are entities posed each drawn frame from the body's animator, between the two frames of the simulation either side of the moment drawn ("How the app draws it", below). The first-person changes are made by which entity a mesh's bone is tied to: the ribcage is the weapon rig's root (which is at the ribcage, turned to the view and squeezed); an arm's bones below the collarbone are the weapon rig's own, which the arms' solver places; each collarbone is an entity under the rig's root that is put, every frame, where the animated collarbone is, seen from the root with the squeeze left out; the neck hangs from the rig's root. `--body` and `--legs` name the bundles (`none` leaves one out), and `--view body` is a capture of the whole figure from three metres off.

One thing found on the way: **the skeleton's root, asked of the animator as an ordinary bone, keeps the clip's travel over the ground**, which the animator takes off its own root bone; the drawn body stood twice as far along a walk as the player until the drawn root was made the animator's own.

**Worn items** (read on 2026-10-10 from `PlayerBody.SlotView.CreateAndParent`, `Dress`, `SkinDress`, `VestSkin`, `BackpackSkin`, `TorsoSkin` and from the bundles of an armour, a backpack and a helmet; a first cut built the same day). What a character wears in a slot of its equipment is shown by the item's own bundle, in one of three ways:

- *A skin.* The bundle's object carries a `DressItem` with two halves: the item as it lies on the ground (`LootPrefab`, plain meshes) and as it is worn (`DressPrefab`). The worn half has a `SkinDress` listing a skin for each level of detail, fullest first, and each skin is a `Skin` like clothing's (a skinned mesh and the paths of its bones on the player's skeleton) or one of three kinds that hold such a `Skin` and several meshes to choose from by what else is worn: a vest's (`VestSkin`: one mesh for over the body, one for over armour), a backpack's (`BackpackSkin`: over the body, over armour, over a vest, over both) and a torso garment's (`TorsoSkin`: bare, under armour, under a vest). "Armour" for that choice is an item in the armour slot or a vest with armour built in. Armour, vests and backpacks are of this kind. The model is put under the body's mesh object and skinned to the skeleton.
- *A model on the head.* Any other item with a `Dress` on it is parented to the slot's bone with no offset and a fixed turn (the quaternion (0.5, -0.5, -0.5, -0.5) in the engine's axes), and the slot's bone is the head for every slot but the holsters, the scabbard and the armband. Helmets, headsets, glasses and the hard face covers are of this kind: plain meshes that ride on the head bone (the cloth face covers, the balaclavas and the Buffalo, are skins of the first kind).
- *A weapon in a holster or on the back* is parented to that slot's bone so that its own weapon root lies on it, and **its renderers are switched off for the player's own character**.

## The feet on the ground (read 2026-10-16; the grounder built 0.27.0 and taken back 0.28.0; the options' `GROUNDED FEET` a height fix, a departure)

**What the game does.** The body is drawn where the character's capsule is, and the capsule counts as on the ground while ground is within its check below it (7 to 15 cm by state; `movement.md`, "What counts as on the ground"), with nothing pulling it down on the flat; after a short drop it can rest that far over the ground, and the feet are drawn there (the eighth recording's start stood 7.62 cm over the terrain). The player prefab carries a foot grounder (FinalIK's `GrounderFBBIK` on `IKController`, working through the prefab's full-body solver), switched by the movement (`GrounderSetActive`: off on a jump, on at the landing, off into prone and on out of it), its quality set to the fastest for one's own character (`GamePlayerOwner`). **It never runs**: in the game's build its `Update` is empty and nothing calls its `Initiate`, so it never joins the solver.

**How the grounder would work** (FinalIK's `Grounding`, read in the build; its settings on the prefab, `trp_data::player::GrounderData`: weight 1, step 0.35 m, height offset 0, foot speed 0.9, prediction 0.3 s, foot rotation weight 1 at speed 10 to 45 degrees, pelvis speed 20, pelvis damper 0, lower pelvis weight 1, lift pelvis weight 0.1):
- *The root's ground*: a cast straight down from above the feet's middle; the character's root counts as near ground while that ground is within twice the step below the start (the step below the feet).
- *Each foot*, every frame: a ray straight down from the step above where the animated foot is, moved on by its flat speed times the prediction, three steps long. How far the root stands over the ground it meets (less the height offset) is the foot's want, held within a step either way, and nought while the root is not near ground. The foot's offset goes toward its want by the foot speed a second and then by that share of the gap a second; it may lift the foot only so far that the foot stays within a step over the root. The foot's goal is its animated place lowered by its offset. Its turn toward the ground's slope is kept within the angle and eased at its speed (the range's tops are level: no turn).
- *The pelvis* goes down by the offset of the foot most lowered, times its lower weight, plus that of the foot most raised times its lift weight, nought while the root is not near ground; eased at the pelvis speed as a share of the gap a second.
- *The legs*: the full-body solver bends each leg to put its foot on its goal, the foot keeping its own turn (`maintainRotationWeight` 1).

**What `GROUNDED FEET` draws** (`feet_down`): the body drawn down by the gap between the character's underside and the ground that holds it, while it is on the ground and no further over it than its ground check reaches, eased by a spring of the game's body-height lag time (0.066 s, `ESTIMATE`). The shoulders and the ribcage the body is drawn with hang from the weapon rig (`body_view::see_collarbones`), so for the character's own eyes the drop stops at the waist (the first spine bone kept where the animation has it; the first-person arms the same with the switch on or off), and seen from outside the whole rig (the weapon, the arms holding it, the shoulders on it) comes down with the body, the eye staying where the game has it. **The grounder above was built and taken back** (0.27.0 and 0.27.1): with the prefab's settings it folded a leg into a squat where a foot was over a drop; with a foot over a drop let hang and the pelvis held to leave each leg 0.8 of its length the squat went, but the solve did not work while sprinting, and with the legs spread wide they twitched and bent backwards, so the simple height fix came back. (A two-bone solve turns the knee in the plane the animated knee makes with the hip and the goal; with the leg near straight that plane is ill defined and flips from frame to frame, the likely cause of the bending backwards. Not looked into further.)

## What is built from this

`states` reads the controller in full: parameters with defaults, states with speed and per-layer blend trees, transitions with conditions, exit times, lengths, offsets and interruption settings, the entry and exit choices of sub-state machines, layers with masks and what they are synchronised with, and the movement-state scripts. `anim` reads a clip's motion curves and reference pose, and can cut a clip down to chosen curves.

`animator` is the animator: parameters, the state machines, blend trees, transitions, root motion, curve-driven parameters, and the pose of a chosen set of bones through the layer stack. It knows nothing about the body; it could run the weapon's controller as well.

`body` runs it on the body's controller for the bones the first-person view needs and exposes what the rest reads: the events that change movement state, the motion, the curves, where the ribcage is, where the weapon is carried, where the right palm is, and the body's camera bone. It reads the clips of the states the movement can reach (370 clips, a fifth of a second to read) and leaves the rest out; the animator never enters a state whose clips were left out.

`movement` no longer changes state by itself or works out its own motion. It raises the flags above, lets the animator run, enters whatever movement state the animator's new state names, and passes the animator's motion through the formulas of `movement.md`.

The watch on the wrist ("The watch on the wrist", above): `watch` reads each hands entry's watch and its prefab, `watch` turns its hands by the time of day, and `watch_view` hangs it on the arm and runs its clock; `trp_data::arms::is_glass` finds the watch's glass, which the hands leave undrawn.

Not built:

- The states left out: vaulting and climbing, interactions and stationary weapons. (Blind fire's four states and its ribcage layer are read since 0.123.0: `blind-fire.md`, "The body".) (A fall has no state of its own in the game: `movement.md`, "Falling".)
- Both arms, the shoulders, the elbows' goals and the left hand's fingers where the body's clips take them are built (`hands-on-weapon.md`, "Whose arm it is"), as is the right hand's hold on the weapon (`weapon-handling.md`, "In the body's hand").
- Direct blend trees (their children share the weight equally here), mirroring, inverse kinematics passes, and the foot grounder. (A transition cut short from the side of the state being entered is built since 2026-10-10: "A transition cut short", above. One cut from the side of the state being left still drops the state that was being entered, where the engine presumably holds that blend too; no recording has one.) Nor is the order of a state's transitions kept when one is cut short: a transition marked as open to those above it in the list ("ordered") is here cut short by any of the state's transitions whose conditions hold, above or below. The turns on the spot are where both could show (a turn begun while the other plays is such a transition).
