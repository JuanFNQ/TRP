# The manual

Every key, every option of the app, every command that looks into the install, and how a recording is made and compared. The README has the short form; this is the long one, moved out of it word for word on 2026-10-13 and kept current since. The scratch scripts and the kept recordings one by one are in `workbench.md`.

## Running

**`Install.bat`**, at the repository's top, sets the app up once (2026-10-16, 0.42.0, the user: "Can we make the installer a little simpler? It's too confusing and include a "play" exe or bat file so we don't have to type the cargo command every time"): it says what it will do and what is needed, and waits for a key before doing any of it (0.42.2, the user: "Make it so the installer waits for an input before beginning, instead of just starting automatically. giving the user time to read"); then it looks for Visual Studio's C++ tools (`vswhere`) and then Rust (`cargo`, also in `%USERPROFILE%\.cargo\bin` for a console opened before Rust was installed), offers each that is missing through winget (`Microsoft.VisualStudio.2022.BuildTools` with the C++ workload, then `Rustlang.Rustup`, the C++ tools first because Rust's own installer asks for them; declined, or without winget, it opens the page to install it by hand and stops), builds the app in release (`cargo build --release -p trp-app`) and asks where the games are (`trp.exe --setup-only`: the questions below, then the run ends). **`Play.bat`** starts the app, `cargo run --release -p trp-app -- <whatever follows Play.bat>`, from the workspace, so the build is made again first only when the code has changed, as after an update; it stops on a key where the run ends in an error, so a double-clicked window leaves its message to read. Both keep Windows' line ends in a clone and in GitHub's zip (`.gitattributes`). By hand, from this folder:

```
cargo run -p trp-app
```

The first build compiles Bevy, and PhysX 4.1 from its source with the C++ build tools (three minutes here; the build folder 4.1 GB, 5.1 GB with the tests, measured from nothing on 2026-10-16; the crates we depend on built without debug information since 0.12.2). The first line a run prints is its version (`TRP 0.10.0`); `--version` prints that alone and stops (how the number goes: "Versions", under "Publishing").

### The first start

Where no install is named (or the one named is not there), the app asks in the console it was started from (`crates/trp-app/src/setup.rs`), one question at a time, each asked again until its answer is a folder of the kind asked for, and each offering for Enter the folder kept from before, and nothing else: no folder is looked for on the drives or worked out from another (the user, 2026-10-17: "no dont do automatic search!", and "make sure the installer asks where each of the folders are"; 0.42.0 had offered the first of the usual folders found on any drive, and asked GAMMA and Anomaly as one answer with Anomaly taken from GAMMA's Mod Organizer; 0.42.1 asks each, as before 0.42.0):

1. **Single Player Tushonka (SPT)**, which is needed: its folder, the one with `SPT_Runtime` and the game's `EscapeFromTarkov.exe` (checked: the game's `EscapeFromTarkov_Data\StreamingAssets\Windows` and SPT's `SPT_Runtime\SPT_Data\database`).
2. **GAMMA**, if there is one: its Mod Organizer folder (checked: `ModOrganizer.ini`). Enter with nothing offered, or `-`, for none.
3. **Anomaly**, if there is one: its own folder (checked: `fsgame.ltx`), asked for itself even where GAMMA's Mod Organizer names one. Enter with nothing offered, or `-`, for none.

A folder may be pasted with Windows' "Copy as path" quotes. The answers go to the workspace's `local` folder (beside the `Cargo.toml` that has `crates`, from wherever the app was started below it), one plain line a file: `eft_dir.txt`, `gamma_dir.txt`, `anomaly_dir.txt`; a question answered with none removes its file. **`--setup`** asks again whatever is kept, what is kept being each question's answer for Enter; **`--setup-only`** asks and ends the run (`Install.bat`). A capture (`--screenshot`, `--scenario`) never asks, nor a run whose input is not a console, nor one with `EFT_DIR` set: those stop with a line saying how to name the install. The files can still be written by hand, in any of the ways an editor or PowerShell saves text (plain, UTF-8 with its mark, UTF-16), or `EFT_DIR`, `GAMMA_DIR` and `ANOMALY_DIR` set in the environment.

**The outfits** (`docs/spec/outfits.md`). Those from S.T.A.L.K.E.R. need to know where that game is: Mod Organizer's folder of GAMMA in `local\gamma_dir.txt` (or `GAMMA_DIR`) and Anomaly's own in `local\anomaly_dir.txt` (or `ANOMALY_DIR`), each a line with the path (`E:\GAMMAEFT`, `E:\AnomalyEFT`). Both are read and never written; what no mod has loose is read from Anomaly's packed archives (`db\*.db*`) in place, unpacked in memory and checked. Three lie in the crate, one for each file in `custom\outfits`: **the Sunrise suit** (`--wear 66f0a5740000000000000101` starts with it on), **the SEVA suit** (`...103`) and **the Telnik** (`...102`), which is the install's own striped top with the install's own bare hands and needs neither folder. Alt and a click puts one on the body armour's slot; taken off (dragged back, or `Delete`), the character's own is back. A suit is then the character's body from outside and its shadow, and in first person its legs up to the waist; **the arms in first person are that game's own arms for the suit** (the file's `arms`), their fingers on the install's own and their size taken off the install's own hand (a line `"arms_size": 1.2` in the file says another, in times the model's own file). **Whatever an outfit has not got (a model not found, a picture missing) is the install's default body or arms**; a line at the start says what each outfit has and what was left. `--wear <id> --bare --view body` is the figure alone from outside. **To set two outfits' hands beside one another in the same pose**, hold a clip still: `--wear <id> --play akm_look --at 2.0 --screenshot ...` once for each (the look all over the rifle, two seconds in; `--at 1.0` shows the left thumb). `EFT_OUTFIT_ARMS=always` in the environment shows an outfit's arms in every view with the upper body left out, to look at them from outside (`--pov first --view side`). **`EFT_OUTFIT_ARMS=both` draws an outfit's arms and the install's own at once**, one through the other: where the suit's skin shows it lies outside the install's, and where the install's shows, inside (`--arms assets/content/hands/hands_bear_telnik/hands_bear_telnik.skin.bundle` makes the install's the bare ones, which tell from a dark glove at a glance). The look at 1.5 s has the open left palm towards the eye, and `--play akm_check_0 --at 2.6` the hand from the thumb's side with its wrist bent. **`--custom-hands off`** starts with the options' switch off (the install's default arms whatever is worn; `on` the other way; without it, as the options' file has it, and on in a capture).

**The inventory's pictures** (`docs/spec/icons.md`) are drawn as the game draws them: each item's own model, in its prefab's own pose, under a copy of the game's icon camera and its three lights, once, and kept as a PNG in `local\icon_cache\v1` (by template and size: `<template>_<w>x<h>.png`). As in the game, **a picture is asked for when the screen first shows the item**: what is carried, and a crate's contents when it is opened; each is read from the cache, or drawn, away from the frame, and **its box shows a spinner until it comes** (the plain shape of its sort is for a thing whose picture cannot be made, and for every thing with `ICON GENERATION` off), in play (the first opening of a crate of weapons draws its pictures one after another over some seconds; later runs read them). Nothing waits for them under the curtain. A suit of S.T.A.L.K.E.R.'s is drawn from that game's own model of it lying on the ground (`world_visual` in its file), read from Anomaly's packed archives, under the same camera and lights. `ICON GENERATION` on the options' `FEATURES` part (or `--icons off`) leaves every picture undrawn and unread. **Delete `local\icon_cache` to have them all drawn again** (after a change to the drawing or the materials); a line at the start says how many were read and how many drawn.

**What goes together is lit** (`docs/spec/inventory.md`, "The box under the mouse, and what goes with it"): with the mouse on a thing in the inventory, or a thing carried, the boxes of what goes with it are orange: for a weapon its magazines, its rounds and the parts that fit it; for a magazine the weapons it fits and its rounds; for rounds the weapons and magazines that take them; by the game's own filters. The box under the mouse is lighter, as the game draws it. **A box blinks** while its move waits on the hands, as the game's does: a weapon put into the slot the hands last drew from, until it has been drawn; the weapon in hand taken out of its slot, until it is put away; it takes no clicks meanwhile. **A run begun with nothing in hand makes no weapon's rig at the start**: each weapon's, the run's own too, is made when it is first hung on a slot the hands take from, and its slot's key pressed meanwhile waits for it; the hands take it once it is all on the graphics card, a few frames later. **`TRP_RENDER_TIMING=1`** in the environment (or a number of milliseconds) prints every frame of the renderer or of the main thread that takes longer than that (20 ms unless told), stage by stage (the interface's stages and when each schedule was reached among them), and every system with a clock of its own that takes a millisecond or more: where a stutter goes. **`TRP_GPU_MEMORY=1`** prints every two seconds what the renderer's allocator holds on the graphics card and the pictures among it (`graphics memory: … MB allocated in … MB of blocks, … allocations; … pictures of … MB`); with streaming on, the app says besides whenever its pictures' share changes (`mip streaming: … pictures, … MB of them on the graphics card of … MB whole`). **`--measure-rigs <crate|all>`** makes ready every weapon's rig of that crate of weapons (`RIFLES`, `PISTOLS` and so on, or `all`) and weighs it, none put into the world, prints a line for each and the sum, and ends the run. **A weapon of one's own's pictures are compressed** as the install's are and kept in `local\picture_cache`: delete it to have them made again (after changing the encoders; a changed picture is made again by itself). With it, a line `samplers:` each time the places for samplers held move (DirectX 12 has 2,048: `docs/findings.md`). **`TRP_ICON_CACHE=<folder>`** gives a run an icon cache of its own (an empty one, to see the pictures made, and the kept one left be); **`TRP_ICON_TRACE=1`** prints every 60 frames where the pictures stand and each pipeline the renderer is still building, which a picture waits on. The orange is the user's wish, after S.T.A.L.K.E.R.; the game has nothing like it, and `COMPATIBLE ITEMS HIGHLIGHT` on the options' `FEATURES` part (or `--feature compatible_items_highlight=off`) leaves it off.

**The view settings come from the install.** The field of view, head bobbing and the two mouse sensitivities are read from the game's own settings as SPT keeps them (`SPT_Runtime\user\sptSettings\Game.ini` and `Control.ini`), so the app starts looking as the game beside it does; where the install has none, the game's defaults (50, 0.2, 0.7, 0.5). What the options tab has kept (`local\options.json`) overrides them for someone at the keys, and the options below override both.

**How it is stepped.** The simulation runs on a frame clock of its own, 120 frames a second whatever the rate of drawing (`trp_sim::Pacer`; `--frame-rate` changes it), because the game's own results change with its frame rate and 120 is the rate every recording was made and compared at. Each of its frames is one frame of the game, and the weapon's springs step once for each 1/60 s physics step that falls in it. What is drawn is the simulation as it stood one physics step (17 ms) before the host's time, blended between its frames, with the view's own turning drawn at once. Two things the game does unevenly on even frames, because it times the player by a clock in whole milliseconds, are evened out in what is drawn and nowhere else: a jump's travel through the air and the body's turn after the view in a jump. With `--hold`, the scripted presses come at set seconds while `--screenshot-frame` counts drawn frames, so pick a late frame. The long account is in `docs/history.md` ("The README's long form").

`xdb <words> [get]` lists the other game's packed archives with their counts of files and the names that have the words (with `get`, each read, unpacked and checked); `ogf` reads a model from them where it is not loose. `icon` prints an item's icon pose (its prefab's `PreviewPivot`) and the object it is on, `studio` the game's icon camera, its lights and its shadow as read from `resources.assets` beside the figures read by hand, `resources <word>` the game objects of `resources.assets` whose name has the word, with their components, read by the engine's own layouts.

**The physics** (`docs/spec/physics.md`): `layers` prints the engine's settings as the install has them (gravity, thresholds, iterations, the solver) and its layers with which meets which; `ragdoll` the player prefab's bodies, colliders and joints with every figure of each; `colliders <template>` an item's model as it lies loose (a weapon with its parts) and every collider on it, with its object, shape, layer, whether a trigger or switched off, and its material. The tool `corpse` (in `trp-physics`) rebuilds a recorded death's corpse in the engine from the recording's first frame after the death and steps it as the game steps, printing four bodies' heights and depths beside the recorded ones every `--every` seconds and the mean drift of all twelve to 0.25, 0.5 and 1 s; `--conventions` tries every way of laying Unity's joint on PhysX's, `--angles` prints each joint's twist from the skeleton's rest and from the pose at death against its limits. `cargo test -p trp-physics` holds the four recorded deaths to their drifts (skipped without `local\traces\courses1`).

**Health** (`docs/spec/health.md`, "Compared with what"): the tool `health_replay` (in `trp-sim`) sets a recording of the medicine course, or of the falls and the wire (course 2: each fall from the recording's own heights, the chances as the game drew them, the wire's cuts as the game made them, listed as tallies), beside the simulation (the character as its first frame has it, the step's hurt, each item where the game's comes in hand, its jumps and sprints, the skills of the install's newest profile, or none with `--untrained`), and prints each effect's states with their times, the game's beside ours, the parts at the end and the largest gaps; `--every <s>` adds the parts, energy and hydration so often. With the install's assets (unless `--no-hands`) it runs each item's own hands beside the recording too (`MedsHands` on the item's rig) and prints, for each use, the animator's states and `Active` with their times, the game's beside ours, when the item left the hands, and the largest gap in how far a state has played. `cargo test -p trp-sim --test health_replay` holds all nine recordings to the game's frames and points, and the twelve uses' hands, and the six of course 2 (skipped without `local\traces\courses1`). **The first build of `trp-physics` compiles PhysX 4.1 from its source** (about five minutes, with the C++ compiler of Visual Studio's Build Tools); later builds take it as built.

`weapon`, `clips` and `states` take a weapon-like prefab's bundle (anything with a `/` in it) in place of an item's id, which is how the game's empty hands are looked at: they are no item of the database.

`item` prints an item of the database by its id or a part of its name: its classes, weight, cells, slots and grids with what each takes. `json` looks into one of the database's files at a path, so many levels deep (in Git Bash, set `MSYS_NO_PATHCONV=1` first, or the path is rewritten).

**A weapon of one's own** is looked at with four more. `fbx <file>` lists a binary FBX file's models, each with where it is, how large and its connected pieces (`records` in place of nothing prints the file's records; `view <png> [pixels a centimetre] [ahead behind above below]` draws it from its left side and from above over a grid of centimetres; `slice <model> <axis> <from> <to> [piece] [points]` gives what of a model lies in a slab, for measuring a feature). `overlay <weapon> <fbx> <the fbx's trigger model> <png>` draws one of the install's weapons with such a model over it. `custom [id]` lists the weapons of one's own, and for one its parts, its weight and its pictures as read (their sizes, their mean colours, and the colour its vertices see). `donor` (in `trp-sim`, since it runs the animator) measures the install's weapons as donors: for each named (every rifle, carbine, submachine gun and machine gun if none), where its trigger, magazine, muzzle and butt are, where the left hand rests, and which hand works the action in a draw and in a reload from empty (`--no-catch` runs it as a weapon without a catch, `--detail` adds every bone that travelled and the palms every twentieth of a second, `--from-bone` gives everything from the weapon's own bone); `donor --overlay <weapon> <png>` draws a weapon as its animator has it at a moment (`--moment idle|draw:<s>|reload:<s>`) with both hands' bones, a model laid over it with `--model <fbx> --place <ahead> <up> <right>`; given the id of a weapon of one's own it draws that weapon, edits and all. **`donor --catalogue [file]`** measures every weapon of the install that way (a minute) and keeps one line for each different set of clips in `local\donors\catalogue.tsv`; **`donor --rank <a weapon's file> [catalogue]`** lists the donors nearest to what that file's `wanted` block asks for (`docs/spec/custom-weapons.md`, "The catalogue of donors").

`keys` prints the install's own key bindings whose name has the part given (the game's name for each, how it is pressed, its keys) and two of its game settings; `states <weapon> parameters` the parameters of a weapon's animator with the kind of each.

`scenes` lists the build's scenes with the file each is (`level<N>`), those whose path has the part given, and prints the inventory screen's equipment panel and its quick-use panel as read. `screen` shows the objects of a scene file whose name has a part, each with what hangs from it so many levels down, how it is laid out on its screen and which scripts are on it: this is how the game's own screens are looked at, since they are in no bundle. `fields` dumps the scripts' own fields of the objects whose path ends so (each word as a whole number and a real number), which is how the engine's own UI scripts (a layout group, an image, a text) were read by their order of fields. The build's own files beside a scene (`sharedassets<N>.assets`) keep no type trees: `healthpanel` and `sceneclips` read their sprites, textures and clips by the trees of the same classes borrowed from a bundle of the install's (`classfind` finds the smallest that keeps one).

`script <bundle> <class> [depth] [items]` prints every script of a class in a bundle as it is stored, with the object it is on: how the player prefab's own figures are looked at.

`weapons [part of a name]` goes over every weapon of the database that has a stock preset (149 in the install read, the weapon of one's own among them; fourteen more have none), assembles each and reads its animator: its class, how many states and clips, and two marks by which weapons with the same set of states, and with the same set of clips, are told. 97 distinct sets of clips and 91 of states.

`ogf <a file, or a path under the other game's meshes>` reads a model of S.T.A.L.K.E.R.'s where that game's folders are set (above): its meshes, each with its vertices, its triangles, its bounds and the picture it names (and where that was found loose, if it was), and its bones at rest, each beside the middle of the vertices that go mostly with it. `skin <bundle>` prints the bones a piece of the character's clothing hangs on, each where it is at rest in the mesh's space: the two are what an outfit's fit is made from (`docs/spec/outfits.md`).

`clips <weapon> <clip> path <the end of a bone's path> [from] [to] [step]` follows one bone through a clip from the clip's data alone, with no simulation and no drawing: every bone above it as the clip has it, one line a time, with where it is in the rig's own frame, its speed and how fast it turns, and how each bone's curves are kept (as cubics from key to key, as samples at a steady rate joined by straight lines, or as one figure). `clips 59d6088586f774275f37482f akm_look path weapon_L_IK_marker 2.55 2.85 0.004` is the left hand's marker through the look's fast turn: its speed breaks at every thirtieth of a second. `series` in place of `path` prints the same tracks' own figures. (From Git Bash a word that begins with `/` is taken for a path and changed: write `anim/weapon`, not `/weapon`.) `texstats <bundle> <word> <folder>` writes each of a bundle's pictures whose name has the word into a folder of scratch as a `.png`, to be looked at (how the bare hands were told from the gloved).

`bodystates` and `bodyclips` look at the body: its animator's states with their transitions and blend trees (`-` as the filter shows all of them; `parameters` in place of `tree` lists the parameters), and its clips with the curves they carry. `blendcheck` sets the computed two-parameter blend weights against the grids the install stores. `hardsettings` prints the game's settings object (to the corpse's figures at its end since 0.11.0). `ragdoll` prints the player's ragdoll as `trp_data::ragdoll` reads it: each body with its mass, drags and colliders, each joint with its axes and limits. `layers` prints the engine's physics layers and which meet which (`globalgamemanagers`), and the physics settings' first figures. `player-scripts <class>` lists every script of a class on the player prefab with the object it is on, its parent, layer and colliders (`player-scripts BodyPartCollider`: the hit colliders). `object <number>` shows an object of `resources.assets` by its number: its class, its name and its first bytes as text. `resources <name> all` writes a game object's components there with every figure.

## Comparing with the game

`hosts/spt-oracle` is a BepInEx plugin for Single Player Tushonka (SPT) that plays scripted input in a raid and records what the game's own controller does, frame by frame. `replay` plays the same scripts through the simulation and reports the gap for each recorded value.

1. Build the plugin (needs the .NET SDK; nothing is copied from the game):

   ```
   dotnet build hosts\spt-oracle\Oracle.csproj -c Release -p:EftDir=E:\spt
   ```

   The result is the folder `local\oracle\stlkreft-oracle`.
2. Copy that folder to `<SPT folder>\BepInEx\plugins\`. This is the one step that puts a file into SPT's folder, and it is yours to do; nothing here does it for you. Delete the folder to remove the plugin. Copying the folder's contents straight into `plugins` works too; the traces then land in `plugins\traces`.

   For each scenario it prints the largest and the root-mean-square gap of every value both sides have: distance travelled, speed, stance, lean, the four springs, sway, the three recoil values, rounds left. **What the replay takes from a trace.** From the header, what the game had: the top speed (which gives the Strength skill), the view settings, the weapon's weight and round, the aiming speed, the rounds loaded; the carried weight is found from the recorded inertia. Frame by frame: the frame times of both clocks (the engine's and the player's whole-millisecond one), the look direction, and which frames had a physics step. From a scenario's first frames, what was carried over into it: the walk's leftover direction rate, the wheel, the stance, the body's facing, the sprint's pace, the pools. Recoil and breathing draw random numbers, so they compare in spread and size, not moment by moment.

A recording's `ground.txt` gives the ground under it: the rise in metres per metre along x and z, a third number for how far over the ground the character stood, or the word `profile` for a recording made over a wall or a ledge, whose ground is then rebuilt from each trace's own path. A recording keeps the scripts it was made with in a `scenarios` folder of its own where they have since changed.

A trace whose header says `point_of_view: ThirdPerson` (recorder 0.7.0 on, the key `\`) is replayed as the character seen from outside (`third-person.md`): what the replay says of the camera, the eye and the field of view is then left out. Every layer of the body's animator starts where the trace's first frames have it (recorder 0.3.0 on), as the base layer always has. `reach_for_vest` in a report is the weight of the layer that reaches for the vest. Switches of the replay: `--traces <folder>`, `--scenarios <folder>`, `--weight <kg>`, `--layers <frame>` (the body animator's layers on that frame), `--own-view` (turn the view from what the script asked, through the simulation's own limits), `--seed <n>`, `--endurance <level>`, `--line <metres>` (the weapon line's length for a recording without it).

## Publishing

Two repositories (the user, 2026-10-14; kept so the same day, over a single public one: GitHub makes a whole repository public or private, never one branch of it). **`stlkreft`, private**, is where the work is done and committed, its whole history with it: the folder `E:\stlkreft`, branch `experimental`. **`TRP`, public**, is a copy of its files without that history, its commits made with GitHub's private e-mail address: a separate clone on disk, `E:\TRP-public`, whose branch `main` began as an orphan. The repository's top folder holds `AGENTS.md`, a short `README.md` pointing into the workspace, `LICENSE` (Apache-2.0, added by the user on 2026-10-14), and since 0.42.0 `Install.bat`, `Play.bat` (with `.gitattributes`, which keeps their Windows line ends) and `PATCH_NOTES.md`, what each release changed for a reader of the public repository, newest first; the workspace is `TRP\`.

```
E:\stlkreft     experimental --git push-------> github.com/JuanFNQ/stlkreft   private: every commit, all the history
     |
     |  at a release, the files alone (fetch, then read-tree)
     v
E:\TRP-public   main --git push, with a tag---> github.com/JuanFNQ/TRP        public: one commit a release
```

**What the public copy holds** (the user, 2026-10-16: "Make sure it only includes what is absolutely needed for someone to build the app; are the recordings necessary for someone else, what about the scenarios and plugin I don't think they are"): the code and its build files (`TRP\crates`, `Cargo.toml`, `Cargo.lock`, `.gitignore`), the figures of the outfits and weapons of one's own the app reads (`TRP\custom`), the licence, the two READMEs, the patch notes, the two scripts that install and start the app, and the documentation the README points to (`TRP\docs\spec`, `manual.md`, `status.md`, `findings.md`). Left out by the `git rm` after the copy: the recording plugin and its scenarios (`TRP\hosts`), any screen recording (`*.mp4`), the AI sessions' brief (`AGENTS.md`), the log, the workbench and the decisions (`docs\history.md`, `workbench.md`, `decisions.md`). The recordings themselves are in `TRP\local`, which git never takes. None of what is left out is needed to build, test or run the app: the one test that reads a scenario skips without it. The copy as it would be published was built and tested on its own (`local/public_check_s86.sh`, 2026-10-16).

**Day to day, `E:\TRP-public` is not touched**: nothing is edited or committed there. The work, its commits and its pushes go to `stlkreft` as always, and the public repository stays as it was until the next release.

**To publish what the private repository has now** (a release), once it is committed there:

```
cd E:\TRP-public
git fetch E:\stlkreft experimental
git read-tree -u --reset FETCH_HEAD
git rm -r -q -f --ignore-unmatch -- "*.mp4" AGENTS.md TRP/hosts TRP/docs/history.md TRP/docs/workbench.md TRP/docs/decisions.md
git status
git commit -m "TRP 0.1.1: <what changed>"
git tag -a v0.1.1 -m "TRP 0.1.1"
git push origin main v0.1.1
```

The number is the one in `TRP\Cargo.toml` at that moment. Then, on GitHub, `TRP` > Releases > Draft a new release, from the tag, with the release's section of `PATCH_NOTES.md` for what changed (the recorder is not published). A release adds its section at the top of `PATCH_NOTES.md` first, in the private repository, for a reader who builds and plays, **short and plain** (the user, 2026-10-17: "simplify the changelog"): one section a published release, a few bullets a subject in everyday words (what can be done or seen; no crates, shaders or measurements), and what is not done or not checked against the game.

**Where `E:\TRP-public` is gone** (found so on 2026-10-14 and again on 2026-10-16), it is cloned again before the steps above: `git clone https://github.com/JuanFNQ/TRP.git E:\TRP-public` (the public history only; `main` follows `origin/main`). A clone has no other local branch, so nothing private is in it until the `fetch`.

`git rm` takes `-f` because `read-tree` has just staged those files changed from the last release, and without it git refuses to drop a staged change (found in the release of 0.42.0); nothing of the copy's own is lost by it. `read-tree` makes the copy's files exactly the private commit's, removed files removed, and the commit made on `main` has only `main` for its parent: the private history is fetched into the copy's own store but is reachable from nothing pushed, so it does not leave the machine. **Never `git pull` or `git merge` from `stlkreft` into the copy**: that would bring the history, and the e-mail in it, along. **Tags are made in the copy only**: one made in `stlkreft` names a commit of the private history, and pushed to `TRP` it would take that history out with it.

**A change made on `TRP`** (someone's contribution merged there on GitHub) comes back the other way as a patch, which takes nothing out:

```
cd E:\TRP-public
git pull
cd E:\stlkreft
git fetch E:\TRP-public main
git cherry-pick <the public commit>
```

`git pull` in the copy is from `TRP` itself, which is safe; the next release's `read-tree` then carries the change back out with everything else.

Before a push, the same checks as the first time: `git log --format="%an <%ae>"` shows only the private address; `git ls-files` shows only the whitelist's kinds of file (`.rs`, `.md`, `.json`, `.toml`, a `.wgsl`, one `.txt`, `LICENSE`, and at the top the two `.bat` and `.gitattributes`), and no `AGENTS.md`, `TRP/hosts`, `history.md`, `workbench.md` or `decisions.md`. Before the commit, the copy as it would be published is set up as a new person sets it up (`local/public_install_s86.sh <folder>`: `Install.bat` with the three folders typed, in a folder away from the workspace, `Play.bat`, the tests on a target of the copy's own).

### Versions

Semantic Versioning below 1.0 (the user, 2026-10-14: "Keep that version updating whenever we do any changes"). One number for all the crates, `version` under `[workspace.package]` in `TRP\Cargo.toml`; the app prints it first (`TRP 0.10.0`), and `--version` prints it alone.

- **Every change raises it**: once for each piece of work that is committed, not for each edit, and the commit's message names it.
- **The middle number** (0.1.x to 0.2.0) when something new can be done or seen (a weapon, a system, a key, a switch of the options), or when what a host, a settings file or a cache in `local\` depends on changes. The last goes back to 0.
- **The last number** (0.1.0 to 0.1.1) for anything else: a fix, a closer match to the game, the documents, the tools, the tests.
- **1.0.0** when the character controller is complete and a host (STALKER's) runs on it without changing it: the first point at which what a host sees can be held still. Until then, as Cargo reads a 0.x number, any step of the middle number may break a host.
- **Each raise leaves a build behind**: Cargo puts a crate's version in its identity, so our crates are built afresh under new names and the old are never deleted (1 to 3 GB a raise before 0.12.2; the build folder had reached 72 GB). `local\sweep_target.sh` takes them away (the regression ends with it); `cargo clean` empties the folder, and the next build takes three minutes.
